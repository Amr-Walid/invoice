## المرحلة 0 — التهيئة (Setup)

**الهدف:** هيكل مشروع نظيف يعمل قبل كتابة أي منطق أعمال.

### المهام
1. إنشاء الحل والمشروع:
   ```bash
   dotnet new sln -n PosSystem
   dotnet new mvc -o src/PosSystem.Web
   dotnet sln add src/PosSystem.Web/PosSystem.Web.csproj
   ```
2. تثبيت الحزم:
   ```bash
   cd src/PosSystem.Web
   dotnet add package Microsoft.EntityFrameworkCore.SqlServer
   dotnet add package Microsoft.EntityFrameworkCore.Design
   dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore
   dotnet tool install --global dotnet-ef
   ```
3. إنشاء مجلدات: `Data/`, `Models/Entities/`, `Models/ViewModels/`, `Services/`.
4. حذف قوالب المشروع الافتراضية غير المستخدمة (`Privacy`, `ErrorViewModel`).
5. ضبط `appsettings.json` بسلسلة اتصال SQL Server.

### معيار «تمّت»
- [x] `dotnet build` ينجح بصفر أخطاء.
- [x] `dotnet run` يفتح صفحة على المتصفح.

## المرحلة 1 — قاعدة البيانات والنماذج

**الهدف:** مخطط قاعدة بيانات مطابق لـ ARCHITECTURE.md مع بيانات أولية إلزامية.

### المهام
1. **الكيانات** (`Models/Entities/`):
   - `Catalog.cs` — `Brand`, `Category`, `Product`
   - `Invoice.cs` — `Invoice`, `InvoiceItem`, `InvoiceStatus`
   - `Coupon.cs` — مع `IsValidAt(DateTime)`
   - `ApplicationUser.cs` — `ApplicationUser : IdentityUser` + `AppRoles`
   - `Tracking.cs` — `StockMovement`, `AuditLog`, `AuditActions`
2. **حقول لقطة السعر (Snapshot)** في `InvoiceItem`: `ProductName`, `Barcode`, `UnitPrice`, `UnitCost`
   → لأنّ تغيير سعر المنتج لاحقًا **يجب ألّا** يغيّر الفواتير القديمة.
3. **`AppDbContext`** يرث `IdentityDbContext<ApplicationUser>`:
   - فهرس فريد على `Product.Barcode` (أهم فهرس في النظام)
   - فهرس فريد مركّب `(BrandId, Name)` على `Category`
   - `HasPrecision(18,2)` لكل الحقول المالية، و`(5,2)` للنِّسَب
   - سلوك الحذف: Invoice→Items **Cascade**، Product→InvoiceItems **Restrict**، Coupon→Invoices **SetNull**
4. **الهجرة:**
   ```bash
   dotnet ef migrations add InitialCreate --output-dir Data/Migrations
   dotnet ef database update
   ```
5. **`DbSeeder`** — بيانات أولية *إلزامية* وقابلة لإعادة التشغيل (Idempotent):
   - البراند: `Infinix`
   - تصنيفاته: `Smartwatches`, `Smartphones`, `Power banks`
   - الأدوار: `Admin`, `Agent` + مستخدمَين تجريبيَّين
   - منتجات وكوبونات نموذجية

### معيار «تمّت»

## المرحلة 4 — نقطة البيع والماسح (POS & Scanner)

**الهدف:** إتمام فاتورة كاملة بالباركود داخل نافذة منبثقة.

### المهام
1. **صفحة المندوب** (`Pos/Index`): مربعان كبيران بارزان — `[فاتورة جديدة]` و`[التقارير]`.
2. **النافذة المنبثقة** (`_PosModal.cshtml`): حقل مسح، جدول السلة، بيانات العميل، كود الخصم، لوحة الإجماليات.
3. **`PosService`**:
   - `LookupByBarcodeAsync` — يرفض المنتج غير الموجود/المعطّل/منتهي المخزون برسائل عربية.
   - `CreateInvoiceAsync` — داخل **معاملة (Transaction)**.
4. **خطوات حساب الفاتورة** (بالترتيب داخل المعاملة):
   1. دمج الأسطر المتكررة لنفس المنتج
   2. **إعادة قراءة الأسعار من قاعدة البيانات** (لا نثق بالمتصفح)
   3. التحقق من كفاية المخزون لكل سطر
   4. بناء أسطر الفاتورة بلقطة السعر
   5. خصم المخزون + تسجيل `StockMovement`
   6. التحقق من الكوبون وحساب الخصم
   7. تقريب الخصم **مرة واحدة** ثم استخراج الإجمالي بالطرح
   8. توليد رقم مرجعي فريد `INV-yyyyMMdd-####`
   9. تسجيل عملية التدقيق (Audit)
   10. `Commit` — أو `Rollback` عند أي خطأ
5. **`pos.js`**: إدارة السلة، تحديث فوري للإجماليات، تنبيه صوتي، مستمع الماسح.

### 🔒 قاعدة الأمان الحاسمة
> الأسعار والخصومات القادمة من المتصفح **تُتجاهل بالكامل**.
> الواجهة ترسل فقط: `(ProductId أو Barcode, Quantity)` + `CouponCode` + `CustomerName`.
> السعر والنسبة يُقرآن من قاعدة البيانات على السيرفر — هذا يمنع التلاعب بالأسعار.

### معيار «تمّت»
- [x] مسح عدة منتجات متتالية يعمل، والكمية تزيد بدل تكرار السطر.
- [x] الحسابات صحيحة: `9050 − 20% (1810) = 7240`.
- [x] رقم الفاتورة فريد وبالصيغة المطلوبة.
- [x] الكمية الزائدة تُرفض والمخزون **لا يتغير** (Rollback سليم).

## المرحلة 5 — وحدة التقارير (Reports Module)

**الهدف:** تقارير للمندوب (فواتيره فقط) وللمدير (شاملة + أرباح).

### المهام
1. **`ReportService`** مع معامل `restrictToAgentId`.
2. **`AgentReportsController`** — يُمرِّر معرّف المندوب الحالي **دائمًا**.
3. **`ReportsController`** (مدير) — كل الفترات: يومي/أسبوعي/شهري/الكل/مخصص + تصدير CSV.
4. **`DashboardController`** — إحصاءات اليوم والشهر، رسم 7 أيام، أداء المناديب، تنبيه نقص المخزون.
5. **تفاصيل الفاتورة** تُظهر: المندوب البائع، العميل، الأصناف، الكميات، السعر قبل/بعد الخصم، نسبة الخصم، والربح (للمدير فقط).

### 🔒 عزل بيانات المندوب
العزل يُطبَّق في **طبقة الخدمة على مستوى الاستعلام**، وليس في الواجهة فقط.
تعديل رقم الفاتورة في الرابط يُرجِع **404** لا بيانات مندوب آخر.

### ⚠️ ملاحظة على المزوّد (Provider)
SQL Server يجمع الأرقام العشرية داخل قاعدة البيانات، أما SQLite **لا يدعم `SUM` على `decimal`**.
لذلك يحتوي `ReportService` على فرع مُوثَّق يجمع على العميل عند استخدام SQLite للتطوير فقط،
مع الحفاظ على التجميع الأصلي عالي الأداء على SQL Server (المزوّد الأساسي).

### معيار «تمّت»
- [x] المندوب يرى فواتيره فقط، ولا يرى الأرباح.
- [x] المدير يرى الكل مع الأرباح والتكلفة.
- [x] تصدير CSV يعمل بترميز UTF-8 BOM (ليفتح صحيحًا في Excel العربي).

3. **الصقل:** رسائل خطأ عربية، أرقام `tabular-nums` بالاتجاه اللاتيني، حماية الإرسال المزدوج.

### ⚠️ خطأ تنسيقي حقيقي اكتُشف بالتحقق البصري
القاعدة `.num { display: inline-block }` كانت تُطبَّق أيضًا على `<td class="num">`،
فتُلغي `display: table-cell` وتُسبِّب **انهيار صفوف الجداول رأسيًا** في الإيصال ولوحة التحكم.
الحل: قصر `inline-block` على العناصر السطرية (`span`, `strong`) وإعادة `table-cell` لخلايا الجداول.
> هذا الخطأ **لا يُكتشَف** باختبارات HTTP وحدها — التحقق البصري كان ضروريًا.

## ترتيب التنفيذ الموصى به (ولماذا)

```
0 التهيئة
└─ 1 قاعدة البيانات ← الأساس؛ أي تغيير لاحق فيها مكلف
   └─ 2 الهوية ← نحتاج «مَن المستخدم» قبل ربط الفاتورة بمندوب
      └─ 3 الإدارة ← نحتاج منتجات قبل أن نبيعها
         └─ 4 نقطة البيع ← جوهر النظام
            └─ 5 التقارير ← تحتاج فواتير فعلية لتُختبَر
               └─ 6 التحسينات ← تُبنى على منطق قائم ومُختبَر
                  └─ 7 الاختبار والصقل
```

**لماذا الإدارة قبل نقطة البيع؟** لا يمكن اختبار المسح بالباركود دون منتجات حقيقية بباركودات فريدة.
**لماذا التقارير بعد نقطة البيع؟** التقارير تحتاج بيانات فواتير فعلية لا وهمية.
