# نظام المبيعات والتقارير | Retail POS & Reporting System

نظام نقاط بيع وتقارير كامل بواجهة **عربية RTL**، مبني على **ASP.NET Core 8 MVC** و**SQL Server** عبر **EF Core**،
مع صلاحيات **ASP.NET Core Identity** بدورَين: `Admin` و`Agent`.

## المميزات

### للمندوب (Agent)
- صفحة رئيسية بثلاثة مربعات كبيرة بارزة: **[ فاتورة جديدة ]** و**[ التقارير ]** و**[ مرتجع ]**
- نقطة بيع في **نافذة منبثقة**: مسح بالباركود، أو **بكاميرا الجهاز**، أو إدخال يدوي
- مسح **عدة منتجات متتالية**، وزيادة/إنقاص الكمية مع تحديث فوري للإجماليات
- **كود خصم بالنسبة (%)** يُتحقَّق منه ويُطبَّق تلقائيًا
- بيانات عميل اختيارية (اسم + رقم هاتف) مع **إكمال تلقائي** من سجل العملاء
- حفظ الفاتورة برقم مرجعي فريد + التاريخ والوقت + المندوب
- **صفحة العملاء:** بحث بالاسم أو الرقم، وكل فواتير العميل مرتبطة برقم هاتفه
- **صفحة المرتجعات:** إرجاع فاتورة كاملة أو أصناف منها، وإعادة الكمية للمخزون
- **تقاريره فقط** — لا يستطيع رؤية فواتير غيره

### للمدير (Admin)
- **البراندات والتصنيفات:** إدارة كاملة (CRUD)
- **المنتجات:** باركود فريد، اسم، **سعر المنتج**، براند، تصنيف، مخزون
- **طباعة ملصق الباركود** لكل منتج من قائمة المنتجات مباشرة
- **أكواد الخصم:** نسبة، تفعيل/تعطيل، حد استخدام، صلاحية زمنية
- **تقارير شاملة:** يومي / أسبوعي / شهري / الكل / فترة مخصصة
- **تفاصيل أي فاتورة:** المندوب البائع، العميل، الأصناف، الكميات، السعر قبل/بعد الخصم، ونسبة الخصم
- **لوحة تحكم:** إحصاءات اليوم والشهر، رسم آخر 7 أيام، الأكثر مبيعًا، أداء المناديب، تنبيه نقص المخزون
- **تصدير CSV** بترميز UTF-8 BOM (يفتح صحيحًا في Excel العربي)
- **العملاء:** سجل موحّد بالاسم والهاتف، مع فواتير كل عميل ومرتجعاته وإجمالي صافي مشترياته
- **المرتجعات:** سجل كامل بكل عملية إرجاع، ومَن نفّذها، وهل أُعيدت للمخزون
- **إدارة المستخدمين** و**سجل العمليات** مع تصفية وبحث ونطاق تواريخ

> **ملاحظة على النطاق:** النطام **لا يتعامل مع التكلفة ولا الأرباح** بطلب صريح.
> سعر المنتج وحده يكفي، والتقارير تركّز على **المبيعات والخصومات** فقط.
> لذلك أُزيلت الحقول `CostPrice` و `TotalCost` و `Profit` و `UnitCost` من النموذج
> وقاعدة البيانات والواجهات والتصدير إلى CSV.

### التحسينات الأربعة المُنفَّذة
| # | التحسين | الوصف |
|---|---------|-------|
| 1 | **تتبع المخزون** | خصم تلقائي عند البيع، ومنع البيع عند عدم كفاية الكمية، مع سجل حركات المخزون |
| 2 | **طباعة الفاتورة** | إيصال حراري **80mm** جاهز للطباعة أو التصدير كـ PDF من المتصفح |
| 3 | **ماسح باركود سريع + كاميرا** | مستمع لوحة مفاتيح يعمل **بدون تركيز يدوي** على الحقل، ويدعم الماسحات التي تُرسل `Enter` أو `Tab` أو لا تُرسل شيئًا، مع حماية من المسح المزدوج + اختصارات `F2`/`F9`/`Esc`. وزر **«الكاميرا»** يفتح كاميرا الجهاز ويقرأ الباركود بصريًا (ZXing محليًا) لمن لا يملك ماسحًا |
| 4 | **سجل التدقيق** | تسجيل الدخول والخروج، البيع، وكل إضافة/تعديل/حذف للمنتجات والبراندات والتصنيفات والكوبونات والمستخدمين، **وطباعة ملصقات الباركود** — مع الاسم العربي الحقيقي وعنوان IP |

## 🏷️ طباعة ملصق الباركود لكل منتج

بجوار **كل منتج** في صفحة `المنتجات` يوجد زر **«طباعة الباركود»** يفتح ورقة ملصقات جاهزة للطباعة.

| الخاصية | التفاصيل |
|--------|----------|
| الصيغة | **CODE-128** (Code Set B) — مطابقة لمواصفة ISO/IEC 15417 مع خانة تحقّق mod 103 |
| المخرج | **SVG متجهي** — يُطبع بدقة الطابعة الحقيقية (600/1200dpi) لا بدقة الشاشة |
| المحتوى | اسم المنتج + الأشرطة + الباركود نصًا + السعر + البراند |
| عدد النسخ | 1 – 60 ملصقًا في ورقة A4 واحدة (لدفعة من نفس المنتج) |
| التبعيات | **صفر** — مولّد مكتوب يدويًا في `Services/BarcodeService.cs` |

### لماذا SVG وليس PNG؟
صورة PNG مُولّدة بدقة الشاشة تُنتج أشرطة مُهترئة (aliasing) عند الطباعة،
والماسح الضوئي يرفضها كثيرًا. الـ SVG متجهي فتُرسم الأشرطة بحدود حادة تمامًا.
ولماذا CODE-128 وليس EAN-13؟ لأن EAN-13 يفرض 13 رقمًا بخانة تحقّق صحيحة،
بينما باركود المنتج هنا قد يكون أي نص بأي طول.

> **للطباعة الصحيحة:** اضبط مقياس الطباعة على **100%** وليس «ملاءمة الصفحة».
> تصغير المقياس يُضيّق الأشرطة فيرفضها الماسح.

**تحقّق مُثبَت:** اختبار `tests/barcode_audit_test.py` لا يكتفي بوجود عنصر SVG في الصفحة؛
بل يرسم كل ملصق على canvas ويُفكّه بمكتبة **ZXing الحقيقية** (نفسها المستخدمة في
ماسح الكاميرا) ويُتحقّق أن النص المفكوك يطابق باركود المنتج حرفًا بحرف —
لكل منتجات النظام (8/8 ناجحة). رسم أشرطة خاطئة يُنتج صورة تبدو سليمة للعين
ويرفضها الماسح تمامًا، ولا يكشف ذلك إلا الفكّ الفعلي.

## 👥 صفحة العملاء — الفواتير مربوطة برقم الهاتف

`/Customers` — متاحة للمدير والمندوب (كل مندوب يرى فواتيره فقط).

**رقم الهاتف هو هوية العميل.** عند حفظ أي فاتورة بها رقم هاتف، يبحث النظام
عن العميل ويربط الفاتورة به تلقائيًا، أو يُنشئه إن كان جديدًا — بلا أي خطوة يدوية.

### تطبيع الرقم (Phone Normalization)

يُخزَّن الرقم مرتين: `Phone` كما كتبه المندوب (للعرض)، و `PhoneNormalized`
بفهرس **فريد** (للمطابقة). لذلك كل الصيغ التالية تُشير إلى **نفس العميل**:

| ما يُكتَب | يُطبَّع إلى |
|-----------|-------------|
| `01001234567` | `01001234567` |
| `+201001234567` | `01001234567` |
| `00201001234567` | `01001234567` |
| `0100 123 4567` | `01001234567` |
| `٠١٠٠١٢٣٤٥٦٧` (أرقام عربية) | `01001234567` |
| `۰۱۰۰۱۲۳۴۵۶۷` (أرقام فارسية) | `01001234567` |

القواعد: تحويل الأرقام العربية/الفارسية إلى لاتينية ← حذف كل الفواصل والمسافات
والرموز ← إسقاط بادئة `00` الدولية ← تحويل كود مصر `20` إلى `0` محلي.

### ما تعرضه الصفحة

- **قائمة:** اسم العميل، رقمه، عدد فواتيره، صافي مشترياته — مع **بحث** بالاسم أو بأي صيغة للرقم
- **تفاصيل العميل:** الاسم، الرقم (قابل للنقر للاتصال)، إحصاءات (عدد الفواتير، عدد القطع، الصافي، المرتجعات)،
  **جدول كل فواتيره** بحالتها وزر «مرتجع» لكل فاتورة قابلة للإرجاع، و**جدول مرتجعاته**
- **إكمال تلقائي في نقطة البيع:** أثناء كتابة الرقم تظهر قائمة العملاء المطابقين،
  واختيار أحدهم يملأ الاسم والرقم فورًا؛ ولو كان الرقم جديدًا تظهر إشارة **«عميل جديد»**

## ↩️ المرتجعات — إعادة الفاتورة والمخزون

المربع الثالث **[ مرتجع ]** في شاشة المندوب (اختصار `F3`)، أو `/Returns`.

### كيف يعمل الإرجاع؟

النظام يستخدم نمط **القيد المعاكس (Reverse Entry)**:
**الفاتورة الأصلية لا تُعدَّل ولا تُحذَف أبدًا** — بل يُنشأ سجل `Return` مستقل
برقم خاص `RET-yyyyMMdd-0001` مرتبط بالفاتورة. هذا يحفظ الأثر المحاسبي كاملًا
ويجعل التقارير قابلة للمراجعة.

**الخطوات الثلاث في الواجهة:**

1. **ابحث عن الفاتورة** — برقمها المرجعي **أو برقم هاتف العميل**
2. **اختر الأصناف والكميات** — إرجاع **كامل أو جزئي**، مع أزرار `+`/`−` لكل صنف
   وسقف تلقائي عند الكمية المتبقية، وحساب **فوري** لمبلغ الاسترداد
3. **اضغط «تم»** — يُنفَّذ الإرجاع ويعود المخزون

### ما يحدث عند الضغط على «تم»

كل ما يلي يتم داخل **معاملة (Transaction) واحدة** — إما ينجح كله أو لا شيء:

| # | الإجراء |
|---|---------|
| 1 | إعادة قراءة الكميات **داخل** المعاملة (يمنع الإرجاع المزدوج من نقرة مكررة أو تابين) |
| 2 | حساب الاسترداد من **سعر الفاتورة الأصلية** مع تطبيق **نسبة خصمها** |
| 3 | **`StockQuantity += الكمية المُرجَعة`** لكل منتج — الأجهزة تُحسَب في المخزون تاني |
| 4 | تسجيل حركة مخزون `StockMovement` بسبب `مرتجع` مرتبطة بالفاتورة وبالمرتجع |
| 5 | تحديث `InvoiceItem.ReturnedQuantity` و `Invoice.RefundedAmount` |
| 6 | تغيير حالة الفاتورة إلى **«مرتجع جزئي»** أو **«مرتجعة بالكامل»** |
| 7 | كتابة سجل تدقيق `مرتجع` باسم مَن نفّذه وعنوان IP |

> **مفتاح «إعادة للمخزون»** مُفعَّل افتراضيًا. يمكن إيقافه للأجهزة التالفة
> التي لا تصلح للبيع مرة أخرى — فيُسترد المال دون زيادة المخزون.

### الحمايات المُطبَّقة

| الحماية | السلوك |
|---------|--------|
| إرجاع أكثر من المتبقي | مرفوض برسالة واضحة، والمخزون لا يتغيّر |
| إرجاع بلا أصناف | مرفوض، وزر «تم» معطّل حتى تُختار كمية |
| الضغط المزدوج على «تم» | محجوب بعلَم في الواجهة + إعادة قراءة داخل المعاملة |
| فاتورة مندوب آخر | `404` — لا يستطيع المندوب إرجاع ما لم يبعه |
| الخصم | الاسترداد يطبّق نسبة خصم الفاتورة، فلا يُسترد سعر كامل لصنف مُخفَّض |
| حدود الاسترداد | لا يتجاوز مجموع المرتجعات صافي الفاتورة |

### أثر المرتجعات على التقارير

كل التقارير تعرض **المرتجعات** و**الصافي بعد المرتجعات** إن وُجدت،
والفواتير المُرجَعة **تظل ظاهرة** في التقارير بحالتها الجديدة (لا تُخفى)
حتى تبقى الأرقام مطابقة للواقع.

## 🛡️ سجل العمليات (Audit Log)

متاح للمدير فقط على `/Audit`، ويجيب عن سؤال **«من فعل ماذا ومتى ومن أي جهاز»**.

| نوع العملية | متى تُسجّل |
|-------------|------------|
| `تسجيل دخول` / `تسجيل خروج` | عند دخول أو خروج أي مستخدم |
| `بيع` | عند حفظ أي فاتورة (مع الإجمالي والخصم وعدد الأصناف) |
| `إضافة` / `تعديل` / `حذف` | على المنتجات، البراندات، التصنيفات، الكوبونات، المستخدمين |
| `طباعة باركود` | عند فتح ورقة ملصقات منتج (مع عدد النسخ) |

كل سجل يحفظ: **التاريخ والوقت بالثانية**، اسم المستخدم، نوع العملية، الكيان ومعرّفه،
تفاصيل وصفية، و**عنوان IP**. والسجل **للقراءة فقط** — لا واجهة لتعديله أو حذفه،
ليصلح كدليل تدقيق موثوق. ويدعم **التصفية بالنوع** و**البحث النصي** و**نطاق تواريخ** والترقيم.

<details>
<summary><strong>ملاحظات تقنية — عيوب أُصلحت في السجل</strong></summary>

**1) السجل كان يعرض البريد الإلكتروني بدل الاسم.**
كان `CurrentUserService.DisplayName` يقرأ مطالبة (claim) باسم `FullName`، وهي
**لم تكن تُصدر أبدًا** — ASP.NET Core Identity افتراضيًا يُصدر `NameIdentifier`
و`Name` (= البريد) والأدوار فقط. فكان الكود يسقط صامتًا على البريد.
الحل: `AppClaimsPrincipalFactory` يُضيف المطالبة عند الدخول، فيُقرأ الاسم
من الكوكيز بلا استعلام قاعدة بيانات في كل طلب.

**2) الترقيم كان يتعطّل عند تفعيل التصفية.**
كان الوسيط يُسمّى `action`، وهو **مفتاح محجوز** في توجيه ASP.NET Core؛
فكان `asp-route-action` في روابط الصفحات يُلغي اسم الأكشن الحقيقي
ويُنتج روابط مكسورة. أُعيدت التسمية إلى `op`.

**3) ترتيب غير مستقر.** عمليتان في نفس الثانية كان ترتيبهما عشوائيًا
بين الصفحات (فيُكرّر أو يُخفي سجلات)؛ أُضيف `ThenByDescending(l => l.Id)`.

**4) «إلى تاريخ» كان سيُسقط يومه.** المقارنة الآن `< التاريخ + يوم` ليكون النطاق شاملًا.

**5) قائمة التصفية كانت تُخفي الأنواع التي لم تحدث بعد** (لأنها مبنية على `DISTINCT`
من القاعدة)، فيظن المدير أن النوع غير مدعوم. الآن = الأنواع المعروفة ∪ الموجودة.

**6) الشريط العلوي كان يعرض البريد أيضًا.** بعد إصلاح المطالبة، صار الشريط
يعرض الاسم العربي نفسه الظاهر في السجل، فلا يختلف ما يراه المستخدم عن ما يُسجَّل عنه.

</details>

> 🐞 **عيب إضافي ظهر أثناء التحقق:** ملف `_ValidationScriptsPartial.cshtml` كان
> يُحمّل `jquery.validate` **بدون تحميل jQuery نفسها** (كانت موجودة في

## التشغيل

### المتطلبات
- [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0)
- SQL Server (LocalDB أو Express أو Docker)
- أداة EF Core: `dotnet tool install --global dotnet-ef`

### 1) سلسلة الاتصال
عدّل `src/PosSystem.Web/appsettings.json`:

```jsonc
{
  "Database": { "Provider": "SqlServer" },
  "ConnectionStrings": {
    // LocalDB (افتراضي — ويندوز)
    "DefaultConnection": "Server=(localdb)\\mssqllocaldb;Database=PosSystemDb;Trusted_Connection=True;MultipleActiveResultSets=true"
  }
}
```

بدائل جاهزة (موجودة كتعليقات في الملف):

```jsonc
// SQL Server Express
"Server=.\\SQLEXPRESS;Database=PosSystemDb;Trusted_Connection=True;TrustServerCertificate=True"

// SQL Server في Docker / بمصادقة مستخدم
"Server=localhost,1433;Database=PosSystemDb;User Id=sa;Password=Your_Strong_Password1;TrustServerCertificate=True"
```

### 2) إنشاء قاعدة البيانات

```bash
cd src/PosSystem.Web
dotnet ef database update
```

> الهجرات مُولَّدة لـ **SQL Server** وهو المزوّد الأساسي للنظام،
> وتوجد في `src/PosSystem.Web/Data/Migrations/`.

| الهجرة | ما تُنشئه |
|--------|-----------|
| `InitialCreate` | الجداول الأساسية: الهوية، البراندات، التصنيفات، المنتجات، الكوبونات، الفواتير، حركات المخزون، سجل العمليات |
| `AddCustomersAndReturns` | جداول `Customers` و `Returns` و `ReturnItems`، وأعمدة `Invoices.CustomerId` / `Invoices.RefundedAmount` / `InvoiceItems.ReturnedQuantity` / `StockMovements.ReferenceReturnId` |

> ⚠️ **مهم عند الترقية:** إن كانت لديك قاعدة بيانات SQL Server قائمة من نسخة سابقة،
> فشغِّل `dotnet ef database update` لتطبيق هجرة `AddCustomersAndReturns`،
> وإلا فستفشل صفحات العملاء والمرتجعات لعدم وجود الجداول.

**لإضافة هجرة جديدة** لاحقًا، حدِّد مجلد الإخراج صراحةً:

```bash
dotnet ef migrations add <MigrationName> --output-dir Data/Migrations
```

### 3) التشغيل

```bash
dotnet run --project src/PosSystem.Web
```

ثم افتح: `https://localhost:5001` أو `http://localhost:5000`

### كيف يعمل الماسح الضوئي؟

الماسح يعمل تلقائيًا **دون الحاجة للنقر على حقل الباركود**، ويتعامل مع كل
أنواع الماسحات الشائعة:

| حالة الماسح | كيف يُعالجها النظام |
|-------------|---------------------|
| يُرسل `Enter` بعد الكود (الأشيع) | الحقل يُسلّم الكود فور وصول `Enter` |
| يُرسل `Tab` بدل `Enter` | يُعامل `Tab` كتسليم للكود |
| لا يُرسل أي مُنهٍ | إنهاء تلقائي بعد سكون `400ms`، بشرط أن يكون الإدخال بسرعة ماسح |
| يُدخل الكود كاملًا دفعة واحدة | يُكتشف بقفزة طول الحقل ويُسلَّم فورًا |
| التركيز على حقل آخر (اسم العميل) | دفعة الماسح تُحوَّل للباركود، والكتابة البشرية تبقى في مكانها |

**تمييز الماسح عن الإنسان** يعتمد على **متوسط** الفاصل الزمني بين أحرف الكود
(`≤55ms` = ماسح). استُخدم المتوسط لا أكبر فاصل، لأن أي تأخّر لحظي من نظام
التشغيل قد يُنتج فاصلًا كبيرًا واحدًا وسط دفعة الماسح فيُصنَّف خطأً كإنسان.

**منع المسح المزدوج:** كل مصادر الإدخال تمرّ عبر دالة تسليم واحدة
(`submitBarcode`) تتجاهل أي كود مطابق يصل خلال `250ms` — فلا يُضاف المنتج
مرتين حتى لو وصلت المسحة من أكثر من مسار في نفس اللحظة.

### 📷 المسح بكاميرا الجهاز (بدون ماسح أجهزة)

بداخل نافذة الفاتورة زر **«الكاميرا»** بجوار حقل الباركود. الضغط عليه يفتح
كاميرا الهاتف أو اللابتوب مباشرةً، وتُقرأ الأكواد **بصريًا** فيعمل النظام
دون شراء ماسح ضوئي.

| الجانب | التفصيل |
|--------|---------|
| الأنواع المدعومة | EAN-13 · EAN-8 · UPC-A · UPC-E · CODE-128 · CODE-39 · ITF · Codabar · QR |
| الكاميرا المفضّلة | الخلفية تلقائيًا على الهاتف (`facingMode: environment`) |
| تبديل الكاميرا | قائمة اختيار تظهر تلقائيًا عند وجود أكثر من كاميرا |
| المكتبة | ZXing‑JS مُضمَّنة محليًا (`wwwroot/lib/zxing`) فيعمل المسح **بدون إنترنت** |
| إيقاف البث | يُوقف كل المسارات عند الإغلاق أو إغلاق النافذة، فلا يبقى مؤشر الكاميرا مضاءً |

> ⚠️ **شرط أمني في المتصفحات:** تشغيل الكاميرا (`getUserMedia`) لا يعمل إلا عبر
> **HTTPS** أو `localhost`. لو فُتح النظام عبر `http://` على شبكة محلية فسيمنع
> المتصفح الكاميرا — والنظام يعرض رسالة عربية تشرح السبب وتقترح البديل
> (الماسح أو الإدخال اليدوي) بدل أن يفشل بصمت.

**منع تكرار الكمية:** الكاميرا ترى نفس الباركود في كل إطار، فلا يصحّ الاعتماد
على مؤقّت زمني وحده. القاعدة المستخدمة: الكود لا يُقبل مرة أخرى إلا بعد أن
**يخرج فعليًا من إطار الكاميرا** (~6 إطارات بلا رؤيته)، تمامًا كسلوك ماسحات
نقاط البيع. لولا ذلك لكانت الكمية تزيد تلقائيًا كل ثانية بينما الكاشير
يوجّه الكاميرا نحو صنف واحد.

<details>
<summary><b>ملاحظة تقنية: لماذا لم نستخدم <code>BrowserMultiFormatReader</code>؟</b></summary>

حلقة `decodeFromVideoDevice` الداخلية في ZXing‑JS تنادي
`MultiFormatReader.decode(bitmap)` **بلا تلميحات**، وهذه الدالة تستدعي
`setHints(undefined)` فتمحو التلميحات المُعطاة للباني — فتضيع
`POSSIBLE_FORMATS` و`TRY_HARDER` ولا يُقرأ أي باركود (تشخيصًا: صفر قراءة مع
22 استثناء `NotFound` على إطار يحتوي باركودًا واضحًا يُقرأ يدويًا بنجاح).

الحل: نُدير حلقة الفك بأنفسنا ونمرّر `hints` **صراحةً** في كل نداء، مع
تصغير الإطار إلى عرض `640px` قبل الفك — الفك على الدقة الكاملة
(1280×960) كان بطيئًا لدرجة إسقاط التبويب.
</details>

## ملاحظات أمنية مُطبَّقة

- 🔒 **أسعار من السيرفر فقط:** المتصفح يرسل `(Barcode, Quantity)` فقط — الأسعار والنِّسَب تُقرأ من قاعدة البيانات، فلا يمكن التلاعب بها.
- 🔒 **لقطة السعر (Snapshot):** كل سطر فاتورة يحفظ الاسم والسعر وقت البيع، فتغيير سعر المنتج لاحقًا لا يُغيّر الفواتير القديمة.
- 🔒 **معاملة ذرية (Transaction):** الفاتورة وخصم المخزون يتمّان معًا أو لا يتمّان — مع `Rollback` عند أي خطأ.
- 🔒 **عزل على مستوى الاستعلام:** المندوب لا يرى فواتير غيره ولا عملاءهم ولا مرتجعاتهم حتى بتعديل الرابط (يُرجِع 404).
- 🔒 **الفاتورة لا تُعدَّل عند الإرجاع:** المرتجع قيد معاكس مستقل، فالأثر المحاسبي الأصلي محفوظ ولا يمكن محو بيع.
- 🔒 **منع الإرجاع المزدوج:** الكميات المتبقية تُقرأ **داخل** المعاملة، فنقرة مكررة أو تابان مفتوحان لا يُرجِعان نفس الصنف مرتين.
- 🔒 **الاسترداد محسوب من السيرفر:** يُقرأ من سطر الفاتورة الأصلية وتُطبَّق نسبة خصمها، ولا يتجاوز مجموع المرتجعات صافي الفاتورة.
- 🔒 **حماية CSRF** على كل الطلبات بما فيها AJAX.
- 🔒 **رسالة دخول موحّدة** لعدم كشف وجود الحساب، وإيقاف مؤقت بعد 5 محاولات.

## ملاحظة تقنية: المزوّد (Provider)

النظام يستهدف **SQL Server** كما هو مطلوب، ويحتوي على مفتاح تبديل للتطوير المحلي:

```jsonc
{ "Database": { "Provider": "SqlServer" } }  // أو "Sqlite" للتطوير
```

> SQL Server يجمع الأرقام العشرية داخل قاعدة البيانات (أداء أفضل).
> SQLite **لا يدعم `SUM` على `decimal`**، لذلك يحتوي `ReportService` على فرع مُوثَّق
> يجمع على العميل عند استخدام SQLite فقط — دون التأثير على مسار SQL Server.
